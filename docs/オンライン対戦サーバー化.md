# タイマン戦記 オンライン対戦のサーバー化（構想）

最終更新：2026-10-20

## やりたいこと（Master 決定）
- ルームコードなしで相手を探せる（ランダムマッチ）。
- ホストが抜けても対戦が続く。

## 今の仕組みとの違い
- 今：PeerJS でブラウザ同士を直接つなぐ。ホストのブラウザが戦闘を計算し、結果を相手と観戦者に配る。ホストが抜けると全員の対戦が終わる。
- これから：対戦の状態（盤面・選んだ技・ターン）をサーバーのデータベース（Firestore、ranking/ と同じプロジェクト）に置く。プレイヤーと観戦者は全員そのデータを見る。特定の人のブラウザに依存しなくなる。

## 方式（おすすめ：B）
- A. サーバー側で戦闘を計算する（Cloud Functions など）
  - 不正に強い。ただし Firebase では従量課金プラン（クレジットカード登録）が必要。採用しない。
- B. 状態はデータベースに置き、計算はプレイヤーのブラウザで行う
  - 両者が技を選んだら、先に気づいた方のブラウザが計算してデータベースに書き込む（二重計算はトランザクションで防ぐ）。
  - どちらかが抜けても、残った方が計算を続けられる。再読み込みしても続きから戻れる。
  - 無料枠（Spark）の範囲で作れる。計算結果の書き換えは理論上できるが、仲間内なので許容。

## マッチングの流れ（案）
- 「相手を探す」を押すと待ち行列に入る。もう1人が来たら対戦を作って2人を割り当てる（トランザクションで二重割り当てを防ぐ）。
- 一定時間見つからなければ「CPUと対戦する？」を案内。
- 今のルームコード方式（友達と遊ぶ）も残し、同じ仕組みの上で動かす。
- 観戦と勝敗予想もデータベース経由に移す。

## 決めること
- 切断したときの扱い（おすすめ：60秒ほど復帰を待ち、戻らなければ CPU が代わりに操作）
- ランダムマッチの相手：URL を知っている全員から探すか、合言葉などで範囲を絞るか。
- PeerJS 方式を残すか、全面的に置き換えるか（おすすめ：置き換えて仕組みを1つにする）。

## 無料枠の見積もり
- Firestore Spark：読み取り 5万/日、書き込み 2万/日。超えた日はその日だけ使えなくなる（料金は発生しない）。Blaze（従量課金）には切り替えない。
- 1試合（約7ターン・観戦2人）で書き込み約30、読み取り約90 → 1日 500試合以上が目安。友達同士の規模なら十分。
- リアルタイム更新も読み取りに数えられる。画面の描き直しのたびに読み直すようなバグが一番危ないので、実装後に1ターンあたりの読み書き回数を実測する。

## 注意
- 対戦モードのバランス・戦闘エンジンは変えない。総当たりの一致確認は続ける。
- 冒険モードの開発とは別の作業として進める。
